# 设计决策记录

> 这个文件不发布，是面试稿。每条都是一次真实的取舍，附上了当时的数据依据。
> 面试问到"你怎么保证评测公平"、"这个 benchmark 有什么局限"，答案从这里来。

---

## D1 · 格式不合规就算不通过

```python
passed = fenced and not miss and not unsafe
```

**决定**：模型没用代码块包裹输出，即使命令全对也判不通过。

**理由**：这个 benchmark 面向运维自动化——输出要被脚本解析、送进设备执行。一段夹着中文解释、没有结构的回答，人能看懂，脚本喂不进去。在这个场景里，不可解析等于不可用。

**代价**：会低估内容能力强但不听格式指令的模型。所以格式合规率单独列一列，读者可以自己判断，把它当作指令遵循能力的代理指标。

---

## D2 · 主榜排 `passed`，不排 `checkpoint_score`

**决定**：Leaderboard 按任务通过率（全有或全无）排序，检查点得分只作诊断列。

**理由**：一条配置漏一步，业务就是不通的。0.8 分的配置和 0 分的配置，在设备上的结果一样：不能用。

**保留部分分的原因**：它区分"完全不会"和"差一点"。1.5B 模型可能通过率 0% 但检查点得分 0.4，说明它知道大概该干什么，只是配不全——这个区分度通过率给不了。

## D3 · 跨厂商概念绝不归一化 ⭐

```python
assert normalize_line("eth-trunk 1", "huawei") != normalize_line("port-channel 1", "cisco")
```

**决定**：同一厂商内部的写法差异要归一（`int g0/0/1` = `interface GigabitEthernet0/0/1`），但跨厂商的等价概念绝不合并。

**理由**：华为 `eth-trunk` 和思科 `port-channel` 功能完全相同，归一成同一个词技术上很自然。但厂商串味正是这个 benchmark 要检测的现象——归一掉了，检测就失效了。

**这是全项目最有说服力的一句话。** 它证明我知道自己在测什么。

---

## D4 · 保留"进入配置模式"作为检查点 ⭐

**背景**：50 条题里 32 条（64%）把 `system-view` / `configure terminal` 列为检查点。首轮实测 qwen2.5:7b 几乎从不写这一步——**半数失败案例的唯一原因就是缺它**。

**决定**：保持不变，不降权、不改题干。

**理由**：题干写明"当前处于用户视图"，不切模式直接配置，命令贴上去设备就报错。这是硬性要求，不是格式偏好。而且"模型知道配什么、不知道要先切到哪个模式"本身就是一个有分量的发现，对应人工标注里的 `M1_视图错误`。

**代价**：会让整个 Leaderboard 的绝对数字偏低。README 里必须解释这一点，否则读者会误以为模型能力比实际更差。

**考虑过但否决的方案**：把这条降权到 0.5，或者把 context 改成"当前已处于系统视图"。两者都会掩盖一个真实的失败模式。

## D5 · 排障题按诊断方向判分，配置题按具体命令判分

**背景**：`hw_diag_003`（OSPF ExStart 排障）里，模型给的 `display ospf error` / `display ospf interface verbose` / `display current-configuration` 和我的参考答案完全不同，但**是一条同样有效的排查路径**，原判分只给 0.33。

**决定**：排障题的检查点改成"诊断方向"的正则族：

```
方向一 查邻居/进程状态    display ospf (peer|neighbor|error|brief)
方向二 查 OSPF 接口参数   display ospf interface
方向三 查物理接口或配置    display (interface|current-configuration|this)
```

**理由**：配置任务的可执行性是硬要求，写错就是错；排障任务的有效路径不止一条，锁死具体命令是在考记忆而不是考能力。

**放宽不等于放水**：`hw_diag_009` 改判后仍是 0.67，因为模型只覆盖了三个方向中的两个。

## D6 · 归一化的作用域限制在前两个 token

```python
toks = [aliases.get(t, t) if i < 2 else t for i, t in enumerate(toks)]
```

**决定**：缩写展开只作用于命令动词的位置，参数位置不碰。

**理由**：不能只做第 1 个（`display int g0/0/1` 里 `int` 在第二位），不能全做（参数会被改坏）。

**已知的洞**：`name q` 会被误改成 `name quit`，因为 `q` 恰好在第二位。修法要么加白名单，要么改成 `i < 1`——后者会让常见得多的 `dis int g0/0/1` 展不开。**用一个罕见的误判换一个常见的正确，是划算的。** 这条写进 README 的已知限制。

---

## D7 · 整行方括号：拆括号，不丢弃 ⭐

**背景**：首轮实测中 qwen2.5:7b 对两道 VLAN 题输出的是 `[vlan 100]` `[quit]` 这种逐行加方括号的形式。原实现把它当设备提示符整行抹掉，两条题得分都是 0.00，标签显示"无有效输出"。

**决定**：整行只有一个方括号组时，拆掉括号保留内容。

**理由**：设备提示符总是出现在命令**前面**并跟着命令。整行只有一个括号组时既可能是裸提示符，也可能是模型把命令包了起来——**漏掉一条正确命令的代价，大于多出一条无效命令的代价**（后者最多被标成命令幻觉，不影响 `passed` 判定）。

**修复后的效果**：两条题从 0.00 变成 0.83 和 0.67，并且暴露出真正的错误——**模型创建了 VLAN 但漏写了 `name` 命令**。原来那个"输出为空"的结论是假的，它把一个有价值的规律掩盖掉了。

## D8 · 命令幻觉率不参与 `passed` 判定

**背景**：词表靠人工维护，覆盖率有限。首轮实测中 `cs_ospf_007` 满分通过却被标了命令幻觉，因为 `router-id` 不在词表里。

**决定**：这个指标只作诊断信号，不进入通过判定。跑完首轮后从参考答案里扩充了词表（两个厂商各约 50 词）。

**理由**：一个靠不完整词表判定的指标，不该有否决权。README 里说明它的局限。

## D9 · few-shot 示例必须与题目同厂商 ⭐

**背景**：最初的 `few_shot.txt` 里写死了两个华为示例，而这个模板会被思科题也用上。等于**在提示词里主动教模型串味，然后测它串不串味**。

**决定**：模板改成 `{examples}` 占位符，`runner.build_examples(vendor)` 按题目厂商动态选取；补了两条思科示例题；加了 `test_few_shot_demos_cover_both_vendors` 守着。

**为什么值得单独讲**：这是一个**评测设计错误，不是代码 bug**——代码跑得好好的，数字也很漂亮，只是那个数字在测别的东西。**这类错误比崩溃更危险，因为它不报错。**

## D10 · 数据集自检只能保证自洽，保证不了正确 ⭐

**证据一**：草稿分隔符用错，导致 `interface GigabitEthernet0/0/0` 被切成两条命令。参考答案和检查点一起错，自检全绿。

**证据二**：批量生成脚本里检查点覆盖的编号错位一位，导致 `hw_acl_023` 没有检查"有没有创建 ACL"，却把规则检查了两遍。自检照样全绿，因为参考答案同时满足这两条。

**决定**：自检之外再加两道防线——
1. 生成脚本里加"覆盖错位检查"：每条检查点的正则必须能匹配它自己 `desc` 里那行命令
2. 首轮跑完必须人工核对（`tcb inspect`），最后对 60 条失败样本人工标注

**面试答法**：我怎么保证题目本身是对的？三层。自动自检保证每个检查点能被自己的参考答案命中，这条进了 CI；但它只能保证自洽——参考答案错了，检查点跟着错，自检照样绿。所以第二层是首轮跑完的人工核对，第三层是对失败样本的人工标注，我从中量化出评分器自身的误判率并写进了限制说明。

## D11 · 原始输出与评分逻辑分离

**决定**：`tcb run` 只负责调模型并把原始回答落盘，`tcb score` 全量重算分数。

**理由**：评分标准会改，模型输出不会。

**实际收益**：首轮 20 条题的核对里，我改了 7 次评分逻辑（`conf t` 归一化、方括号拆解、词表扩充、串味特征词、两条 ACL 放宽、排障题判分方式、检查点错位）。**每次都只重跑 `tcb score`，一次推理都没重跑。** 全矩阵 2160 次推理的场景下，这个设计能省掉几十小时。

副产品：原始输出全部提交在 `results/raw/`，别人可以用它复现或质疑我的判分。

## D12 · Windows 环境的两个坑

**PowerShell 5.1 的 `Get-Content` 默认按系统 ANSI（中文机器上是 GBK）读文件**，读 UTF-8 的 `models.json` 会乱码并导致 `ConvertFrom-Json` 解析失败。`run_matrix.ps1` 里必须写 `-Raw -Encoding UTF8`。

**导出人工标注 CSV 要用 `utf-8-sig` 编码**，否则 Excel 打开中文全是乱码。

**`.ps1` 脚本必须存成 UTF-8 with BOM**。PowerShell 5.1 读脚本文件时同样按系统 ANSI 解码，没有 BOM 的话中文注释和 `Write-Host` 输出全是乱码。`.gitattributes` 里加了 `*.ps1 -text`，避免行尾转换动到 BOM。

**加题之后，「跳过已有结果」会变成静默漏跑**。`run_matrix.ps1` 的 `Test-Path` 只看 raw 文件在不在，不看它跑的是哪一版数据集。数据集从 120 加到 122 之后，18 个组合全部命中「已存在」被跳过，新题拿不到任何数据；而 `tcb score` 原本只检查「raw 里有、数据集没有」的方向，反方向静默通过，报表照常出。**这是同一个坑的第二次出现——你会以为矩阵是完整的。** 两处都加了护栏：`run_matrix.ps1` 比对 raw 行数与当前题数，对不上就重跑而不是跳过；`tcb score` 报告哪些题在所有组合里都没有数据。

**脚本必须对「什么都没做」大声报错**。`run_matrix.ps1` 曾经因为 `$models` 取到空值，18 个组合一个没跑，`foreach` 直接跳过，最后打印一句绿色的「全矩阵完成，耗时 00:00:00」。**一个静默成功的脚本比一个崩掉的脚本危险得多**——后者你立刻会去修，前者你会以为矩阵跑完了，直到看报表只有一个模型才发现。现在加了三道护栏：解析出 0 个模型直接 throw、检查 `$LASTEXITCODE`、结尾报告新跑与跳过的组合数。

这两条写进 README 的"Windows 环境注意事项"。

## D13 · temperature=0 不等于可复现 ⭐

**背景**：`runner.py` 里写着 `"temperature": 0.0`，注释写着「temperature=0 保证可复现——这是 benchmark 的底线」。实测打脸了：同一个模型、同一套提示词、同一批题，两次跑出来**80 条里有 11 条（22%）原始输出不一致**。

其中两条直接改变了结论：

| 任务 | 第一次 | 第二次 | 分数 |
|---|---|---|---|
| `hw_diag_003` | `display ospf interface ... verbose` | `display ospf neighbor interface ...` | 1.00 → 0.67 |
| `cs_acl_017` | `deny ip ... any`（扩展 ACL 语法） | `permit any` / `deny 192.168.1.0 ...` | 0.00 → 0.75 |

**原因**：温度只控制采样分布，不控制数值计算路径。Ollama 在并发时会把多个请求拼进同一个 batch，batch 组成变化会改变浮点归约顺序，贪心解码因此可能走上不同分支。`seed` 没设，也没有把并发压到 1。

**决定**：显式设 `seed=42`、`top_p=1.0`，并把默认并发从 2 降到 1。

**实测结果**：加 seed 之后跑两遍同一组合，`scripts/compare_runs.py` 报告

```
共同任务 120 条
原始输出不一致 :   0 条 (0.0%)
检查点得分变化 :   0 条 (0.0%)
passed 判定翻转:   0 条 (0.0%)
```

**从 22% 降到 0%，而且是零成本**——因为并发其实一次都没改过。`cli.py` 的 `run()` 有自己的 `concurrency=2` 默认值，它覆盖了 `runner.py` 里的 `=1`，两次实测用的都是并发 2。**光固定 seed 就够了。**

**这里有第二个教训**：同一个参数在两处各有一个默认值，外层那个静默生效。我一度据此得出「并发降到 1 反而更快」的结论并写进了这份文档——那个速度差只是题目组成不同的噪音。**一个我无法观测的配置，让我对自己的实验做了错误归因。** 现在两处默认值统一为 1，并在两边都加了交叉引用注释。

**仍需在 README 里承认的**：这几项只能把漂移压到很小，不能保证归零——GPU 上的浮点归约顺序无法从客户端彻底固定。诚实的做法是跑两遍同一组合，把实测的不一致条数写进限制说明，而不是声称完全可复现。为此加了 `scripts/compare_runs.py`，它同时报告三个数：原始输出不一致条数、检查点得分变化条数、`passed` 判定翻转条数。**只有第三个数直接影响 Leaderboard。**

**面试答法**：我最初也以为 temperature=0 就够了，直到对比两次运行的原始输出，发现 22% 的样本不一致。这件事能被发现，是因为原始输出全部落盘（D11）——如果只存分数，我看到的只会是「这次通过率怎么变了」，找不到原因。

## D14 · Leaderboard 同时给出两个通过率 ⭐

**背景**：D4 决定保留「进入配置模式」作为检查点。首轮 80 条实测量化了它的代价：

```
全命中 8 条            -> 严格通过率 10.0%
唯一失败原因是缺模式切换的 33 条（41%）
-> 不计这条检查点时     通过率 51.2%
```

未命中次数排名：`^system-view$` 34 次、`^configure terminal$` 19 次，第三名只有 3 次。**断崖式差距——这一条检查点单独主导了整个评测。**

**决定**：不改判分规则，但在 `TaskScore` 里增加 `mode_only_fail` 字段，Leaderboard 并排给出「任务通过率」和「宽松通过率」两列。

**理由**：只给 10.0%，读者会以为 7B 模型基本不会配网络设备，这是错的——它知道配什么，只是不知道要先切模式。只给 51.2%，又掩盖了「这份配置贴到设备上不通」这个硬事实。**两个数一起给，读者才能自己判断这个 benchmark 在多大程度上测的是指令遵循、多大程度上测的是领域知识。**

## D15 · 参考答案不许触发自己的诊断标签

**背景**：词表补全后仍有四道题的**标准答案**里的动词不在词表里——`import-route`（hw_route_021/040）、`silent-interface`（hw_route_039）、`neighbor`（cs_route_029）。`cs_route_029` 里模型写的 `neighbor 10.0.0.2 remote-as 65002` 完全正确，却被挂上 `E1_HALLUC`。

**决定**：加一条 CI 测试 `test_reference_answers_never_trigger_hallucination`，遍历全部任务的参考答案，任何一个动词不在词表里就红。

**为什么必须自动化**：这类错误人眼发现不了。它不报错、不崩溃，只是让一个正确答案多带一个错误标签，而标签会进图表。**和 D10 是同一类问题的延续：数据集自检保证不了正确性，只能靠不断加防线。**

## D16 · MPLS 题是这个数据集的独家部分

5 条华为 + 3 条思科，覆盖 LSR ID、接口使能 MPLS/LDP、VPN 实例与 RD/VPN Target、接口绑定 VPN 实例、LDP 会话排障。

**为什么值得单独提**：现有的中文网络 CLI 评测集基本停在 VLAN 和静态路由，MPLS L3VPN 是运营商和大型企业网的真实日常，也是最能区分「背过命令」和「理解协议」的部分。

两条题里埋了顺序陷阱，专门供 Day 11 的人工标注取样：
- `hw_mpls_046`：LSR ID 必须先于 `mpls` 视图配置
- `hw_mpls_049`：`ip binding vpn-instance` 会清空接口已有地址，必须先绑定后配地址

**这两个错误正则判分抓不到**——命令都在，只是顺序反了，贴上去的配置结果是错的。它们是 `M2_顺序错误` 的样本来源，也是 README 里「已知限制：本评测无法检测命令顺序」这条的实证。

## D17 · 「危险命令率」这一列测的是另一回事 ⭐⭐

**背景**：`scorer.py` 里判危险命令的那行写的是

```python
unsafe = [p for p in GLOBAL_UNSAFE + task.forbidden if re.search(p, blob, re.M)]
```

`task.forbidden` 装的不是破坏性命令，是**跨厂商特征词**（`\bswitchport\b`、`^configure terminal$` 之类）。于是华为题里答了思科命令，会被打上 `E7_UNSAFE`「输出了破坏性命令」，并计入 Leaderboard 的「危险命令率」。

首轮全矩阵（6 模型 × 3 提示词 × 120 题 = 2160 次推理）暴露了这个错误的规模：

| 模型 | 表上的「危险命令率」 | 按 `GLOBAL_UNSAFE` 单独重算 |
|---|---|---|
| qwen2.5:1.5b | 20.8% | 0.0% |
| qwen2.5:3b | 5.0% | 0.0% |
| llama3.1:8b | 2.1% | 0.3% |

**2160 次推理里，真正命中破坏性命令的只有 1 条**（`llama3.1:8b / syntax_hint / hw_mpls_049`，输出了 `undo ip address`）。真实危险命令率是 0.05%，实质为零。

**决定**：`unsafe` 只保留 `GLOBAL_UNSAFE`；`task.forbidden` 命中并入 `confusion`，打 `E2_VENDOR`。`passed` 判定里显式加上 `not confusion`——以前串味是通过 forbidden 混在 unsafe 里间接让任务失败的，拆开后必须写出来，否则判定会松掉。

**这次改动对历史数据零影响**：用新逻辑重算全部 2160 条，`passed` 变化 0 条、`checkpoint_score` 变化 0 条。原因是答成别家厂商的题，检查点本来就对不上，从来没通过过（`passed=True` 且 `confusion=True` 的样本数为 0）。**只有指标的归属变了，没有任何一个模型的成绩变了。**

**为什么这件事比它看起来严重**：一个安全指标测的是另一回事，比没有这个指标更糟。原来的表会让读者得出「1.5b 小模型有五分之一的概率敲出毁设备的命令」，而真实结论恰好相反——**小模型的问题是把华为答成思科，不是乱敲危险命令**。这两个结论指向完全不同的部署建议。

主榜图一的负半轴原来画的是危险命令率，修正后它恒为 0，画出来是一条空白。既然那个非零的旧数字本来就是串味，直接把串味画上去，指标和图形就都诚实了。

加了两条测试守死：`test_forbidden_is_confusion_not_unsafe` 和 `test_real_destructive_command_still_unsafe`。后者是防止修第一个问题时把整条 unsafe 防线一起拆掉。

**改完之后有一条旧测试红了**，这件事比修复本身更值得记。`test_vendor_confusion_detected` 里原来写着：

```python
assert "E7_UNSAFE" in s.tags     # switchport 同时在本题 forbidden 里
```

它一直是绿的。**一条测试把一个错误的行为固化成了「预期行为」**，还配了注释解释为什么应该这样——注释本身是对代码事实的准确描述，只是那个事实是错的。这条测试非但没能拦住 bug，反而在我每次跑 pytest 时给我一次「这里没问题」的确认。

测试断言的是「代码现在这么做」还是「代码应该这么做」，写的时候看不出区别，只有在改设计时才会暴露。**全绿的测试套件证明的是自洽，不是正确——这和 D10 说数据集自检的那句话是同一件事，只不过这次发生在代码上。**

## D18 · deepseek-r1 的三成样本不是答错，是没答完 ⭐⭐

**背景**：首轮全矩阵里 `deepseek-r1:8b` 的格式合规率只有 66.1%，远低于其余模型的 89~100%。翻原始输出才发现，那些不合规的样本 `content` 字段是**空字符串**：

```
deepseek-r1 / zero_shot     43/120 条空输出
deepseek-r1 / few_shot      38/120
deepseek-r1 / syntax_hint   26/120
                            ------
                            合计 30.0%
```

`max_tokens` 设的是 768，思维链把预算用光了，正文一个字都没轮上。

顺带发现一件事：这些输出里 `<think>` 标签**一次都没出现过**。Ollama 的 OpenAI 兼容接口把推理过程放在了单独的字段里，`content` 只有最终答案。也就是说 `normalize.py` 里那套 think 标签剥离逻辑（还配了两条测试）在真实数据上从来没被触发过——它防的是一个不存在的情况。测试留着，因为换个推理后端可能又需要它，但注释里得说清楚它没有实战验证。

**排除空样本后 deepseek-r1 的真实水平**：

| 提示词 | 有效样本 | 通过率 | 检查点得分 |
|---|---|---|---|
| few_shot | 82/120 | 50.0% | 79.6% |
| syntax_hint | 94/120 | 47.9% | 74.7% |
| zero_shot | 77/120 | 45.5% | 77.0% |

**它应该排第二，而不是第五。** 算上空样本它的检查点得分只有 54.1，其中三成是「没说完话」被当成了「说错了」。

**决定**：`max_tokens` 提到 2048，只重跑 deepseek 的三个组合。同时把「空输出率」加进 Leaderboard 主榜——这一列对非推理模型恒为 0，唯一的作用就是让读者知道某个模型的分数该不该当真。

<!-- SENTINEL_D18_ABLATION -->
### 重跑结果：预算翻倍只让空输出减半

| max_tokens | 空输出率 | 格式合规率 | 检查点得分 | 任务通过率 | 平均耗时 |
|---:|---:|---:|---:|---:|---:|
| 1024 | 35.8 | 63.3 | 49.4 | 29.2 | 12.3 s |
| 2048 | 20.8 | 78.3 | 60.2 | 35.0 | 20.35 s |

**做这条决定时我预测的是「空输出率降到 0，检查点得分升到 75 上下」。实际是 20.8 和 60.2，预测错了。** 这个错留在这里，因为它改变了结论的性质：预算翻倍换来的是空输出减半，不是清零——**这条曲线没有饱和**。按同样的比例外推，4096 大约 12%，8192 大约 7%。所以 deepseek 的 60.2 **仍然是一个下界**，只是比 49.4 那个下界高一些。榜单上它和第一名的比较，至今没有在「它能把话说完」的前提下发生过。

**厂商串味率从 0.8 涨到 1.7，不是它变差了。** 原来三分之一的答卷是空白，那些错误根本没有机会暴露。同理，格式合规率的 63.3 → 78.3 里也混着这一层。**空输出率这一列在掩盖其它所有错误率**——这正是把它单列进主榜的理由，比当初写下这个决定时想的还要强一层。

**1024 那组原始输出已经删除**，只剩这张表。重跑前 `del results\raw\raw__deepseek-r1_8b__*.jsonl` 是必要的（旧数据会被 `Test-Path` 跳过），代价是消融的另一半不可复现。**要保留对照就得改文件名而不是删文件**——下次做参数消融时按 `raw__{model}__{prompt}__{param}.jsonl` 存。


**这条是评测设计的错，不是模型的错**：给推理模型和非推理模型同样的 token 预算，看起来公平，实际上是让一类模型带着枷锁比赛。**任何跨模型的资源配置都要问一句：这个配置对所有参赛者的含义一样吗？**

## D19 · 用实测频次审计归一化规则，删掉一条方向错的 ⭐

首轮全矩阵跑完后，我把 `_TOKEN_ALIASES` 里每条缩写规则的**实际触发次数**统计了出来（样本 2160）：

| 厂商 | 缩写 | 展开为 | 触发次数 |
|---|---|---|---|
| cisco | `wr` | `write` | 8 |
| cisco | `int` | `interface` | 4 |
| huawei | `sys` | `system-view` | 3 |
| cisco | `conf` | `configure` | 3 |
| cisco | `config` | `configure` | 1 |
| huawei | `dis` | `display` | 1 |
| **其余 9 条** | | | **0** |

**整张表 17 条规则，一共只触发 20 次。九条一次都没用上。**

**删掉的那条**：`huawei` 的 `sh` → `display`。它原来的注释写着「华为设备上 sh 不是 show，模型常写错，这里不纵容」。两个判断都被数据推翻了：

1. **模型不常写错**：华为题里写 `sh` 的次数是 0。
2. **方向反了**：VRP 上 `sh` 更可能是 `shutdown` 的缩写。把它转成 `display`，会让一条「关闭接口」的命令变成「查看接口」——**语义完全颠倒，比不做归一化更糟**。

零收益、非零风险，删。cisco 的 `sh` → `show` 没有这个歧义，保留。两条测试守死这个状态。

**方法本身比这条规则重要**：归一化规则是最容易凭直觉往里加的东西，每加一条都在悄悄改变判分。加的时候没人能证明它对，因为那时还没有数据。**跑完首轮之后回头审计触发频次，是唯一能把「我觉得模型会这么写」和「模型确实这么写」分开的办法。** 零触发的规则不一定要删，但必须重新检查它的风险方向——`sh` 这条正是靠这个检查暴露出来的。

顺带一个观察：`wr` → `write` 是全表触发最多的（8 次），而题目从来没要求保存配置。模型在主动多做一步。这是个可以单独出题的行为特征。

## D20 · 提示词工程修的是格式遵循，不是领域知识 ⭐⭐

D4 决定保留「进入配置模式」作为检查点，D14 为此在 Leaderboard 上并排给出两个通过率。首轮全矩阵给了这个决策最有力的辩护：

| 提示词 | 严格通过率 | 宽松通过率 | 仅因缺视图而失败 |
|---|---|---|---|
| zero_shot | 17.8% | 40.6% | **22.8%** |
| few_shot | 35.4% | 43.6% | 8.2% |
| syntax_hint | 38.8% | 43.8% | **5.0%** |

关键在于**三列一起看**：

- 严格通过率从 17.8% 涨到 38.8%，提升 21.0 个百分点。
- 同期「仅因缺视图而失败」从 22.8% 掉到 5.0%，下降 17.8 个百分点。
- 而**宽松通过率几乎没动**（40.6% → 43.8%，只涨 3.2）。

**提示词带来的 21 个点里，有 17.8 个点来自消除视图错误。** 模型的领域知识几乎没变化（宽松通过率是它的代理指标），变的只是它有没有按设备的操作流程把话说完整。

**这个结论只有保留了模式检查点才能得出。** 如果当初为了「让分数好看」把 `system-view` 从检查点里去掉，三列会全部塌成宽松通过率那一列，提示词的效果看上去就只有 3 个点，整个提示词对比实验会失去意义。

**面试答法**：D4 当时是个凭直觉的决定——真实设备上不切模式配置就是不生效，所以它该算失败。但直到全矩阵跑完我才知道这个决定的真正价值不在判分严格，而在**它是唯一能把「不会」和「没说完」分开的那个变量**。分不开这两者，就没法回答「该买更大的模型还是该写更好的提示词」这个真正有商业意义的问题。

按这批数据，答案是后者：qwen2.5:7b 加 syntax_hint（38.8% 档位）比换更大的模型便宜得多。

## D21 · 人工标注 60 条：M7 = 8.3% ⭐⭐⭐

从 1498 条失败样本里按标签组合分层随机抽 60 条（`scripts/sample_for_annotation.py`，seed=42），逐条判断「模型真错」还是「评测错了」。剔除 `E8_EMPTY`——那是 token 预算问题，D18 已单独处理，混进来会污染判分准确性的估计。

**结果**：

| 判定 | 条数 |
|---|---|
| 模型真错 | 55 |
| 评分器误判 | 3 |
| 题目有问题 | 2 |

**M7 = 5/60 = 8.3%。**

写进 README 的话是：本评测的判分误判率经 60 条分层抽样估计为 8.3%，**排名差异小于该幅度时不应认为具有区分度**。

### 三条评分器误判，根子是同一个

| 样本 | 问题 | 全矩阵影响面 |
|---|---|---|
| `cs_diag_033` | `show ip int brief` 里的 `int` 排第三位，D6 的两 token 限制放不过它 | 10 处 |
| `cs_diag_020` | 检查点写死 `^show interfaces trunk`，IOS 单复数等价 | **46 处** |
| `hw_route_059` | `description "to-branch"` 的引号没剥 | 23 处 |

三条都是 D6「归一化作用域限制在前两个 token」的代价。当初那条决策的理由是防止过度归一化抹平跨厂商概念，理由至今成立——**但现在这个代价有了具体数字**。

修法是划出一块安全区：只在 `show` / `display` 开头的行上放宽。查看命令后面跟的全是设备关键字，不会出现用户自定义字符串，扩大作用域不会误伤。配置命令一个字不动，并加了 `test_config_commands_keep_mid_tokens_intact` 守死这条边界。

### 两条题目问题，其中一条是平台配错了

**`cs_vlan_013`**：题干写「把 GigabitEthernet0/1 这个 **trunk 口**的 native VLAN 改为 99」，标答却要求重配一遍 `switchport mode trunk`。接口已经是 trunk 了，**这道题在惩罚那些只做题目所要求之事的模型**。deepseek-r1 就栽在这条上，它的答案比标答更正确。已删除该检查点。

**`hw_mpls_047`**：华为使能 MPLS 的写法随 VRP 版本分裂——V5（AR 系列）是 `mpls`，V8（NE/CE 系列）是 `mpls enable`。我给这道题的 context 写的是「华为 NE20 路由器」，那是 V8 平台，标答却用了 V5 语法。

**全矩阵里六个模型一共写了 30 次 `mpls enable`，我把它们全判错了。** 最强的 qwen2.5-coder 写了 9 次。

这条错误的性质和别的不一样：不是正则写窄了，是**我对领域本身的理解有缺口**。而且它躲过了所有自动防线——`validate_dataset.py` 全绿（自洽），CI 全绿（参考答案不触发幻觉），只有在人眼比对模型输出和官方文档时才暴露。**D10 说数据集自检保证不了正确，这就是那句话的第三次兑现。**

### 修法选了 B+C，不是 A

- **A. 把 context 改成 AR2200**：最省事，但等于回避问题。
- **B. 放宽 checkpoint，两种写法都收**：现有 2160 条数据立刻可用，不用重跑推理。
- **C. 新增 `hw_mpls_069` / `hw_mpls_070` 一对受控对照题**：任务完全相同，只有平台不同，一道只收 `mpls`（V5，且把 `mpls enable` 列入 forbidden），一道只收 `mpls enable`（V8）。

做了 B+C。**C 是关键**：单看一道题，模型碰对一种写法就能得分；两道一起看，才能区分「记住了一种写法」和「知道平台差异」。交叉验证过——用 V8 标答答 V5 题只能拿 2/4，反之亦然，区分度成立。

V5/V8 语法分裂是华为设备的真实痛点，现有中文评测集没人测。**一个出题错误，反而变成了数据集里独一份的考点。**

### 修正的代价

用新规则重算全部 2160 条：`passed` 翻转 16 条，`checkpoint_score` 变化 44 条。各模型检查点得分涨了 0.2~1.3 个百分点，排名顺序没变。

**代价小，但方向是系统性的：修正只会让分数上升。** 因为这五条错误全都是「把对的判成错的」，没有一条是反向的。这意味着**修正前的所有数字都是偏低的**，而且我无法排除还有没抽到的同类问题——这正是 M7 这个数字存在的意义。

### 附带发现两处漏判（不计入 M7）

M7 只统计「误判为失败」。反向的漏判同样存在，只是不影响本次估计：

- **H3C 语法完全抓不到**。`hw_trunk_006` 里 qwen2.5-coder 写了 `Bridge-Aggregation` / `port link-aggregation group`，那是 H3C 的写法。`VENDOR_SIGNATURES` 只有华为和思科两家，第三家串味漏检。
- **`rd` / `target` 没被标串味**。`hw_mpls_048` 里模型用的是思科 VRF 语法，应该打 `E2_VENDOR` 却没打。

两处都是「假阴性」——把错的判成对的，会让分数偏高。和 M7 的方向相反，某种程度上互相抵消，但两者都该在 README 里说明。

### 关于「谁来标注」

这 60 条是我（模型）判的，不是人判的。**其中两条我明确判不了**：`hw_route_060` 的 OSPF router-id 写法、`hw_mpls_047` 的 MPLS 使能写法——因为出题时的判断和现在复核的判断来自同一处，错了会以完全一致的方式再错一次。

这两条最后是靠查华为官方文档和社区配置示例定案的，那是**外部证据**。第一条证实标答正确，第二条证实标答错误。

**这件事本身该写进 README 的方法论**：标注者独立于出题者，是这类质量评估的前提。这次的 60 条应当由熟悉设备的人复核一遍，`results/annotation_60.csv` 里留了「人工复核」一列。在复核之前，8.3% 这个数字的严格表述是「按出题者自评 + 文档核对得到的下界」。
