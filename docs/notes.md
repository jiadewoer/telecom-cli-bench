# 设计决策记录

> 这个文件不发布，是面试稿。每条都是一次真实的取舍，附上了当时的数据依据。
> 面试问到"你怎么保证评测公平"、"这个 benchmark 有什么局限"，答案从这里来。

---

## D1 · 格式不合规就算不通过

```python
passed = fenced and not miss and not unsafe
```

**决定**：模型没用代码块包裹输出，即使命令全对也判不通过。

**理由**：这个 benchmark 面向运维自动化——输出要被脚本解析、送进设备执行。一段夹着中文解释、没有结构的回答，人能看懂，脚本喂不进去。在这个场景里，不可解析等于不可用。

**代价**：会低估内容能力强但不听格式指令的模型。所以格式合规率单独列一列，读者可以自己判断，把它当作指令遵循能力的代理指标。

---

## D2 · 主榜排 `passed`，不排 `checkpoint_score`

**决定**：Leaderboard 按任务通过率（全有或全无）排序，检查点得分只作诊断列。

**理由**：一条配置漏一步，业务就是不通的。0.8 分的配置和 0 分的配置，在设备上的结果一样：不能用。

**保留部分分的原因**：它区分"完全不会"和"差一点"。1.5B 模型可能通过率 0% 但检查点得分 0.4，说明它知道大概该干什么，只是配不全——这个区分度通过率给不了。

---

## D3 · 跨厂商概念绝不归一化 ⭐

```python
assert normalize_line("eth-trunk 1", "huawei") != normalize_line("port-channel 1", "cisco")
```

**决定**：同一厂商内部的写法差异要归一（`int g0/0/1` = `interface GigabitEthernet0/0/1`），但跨厂商的等价概念绝不合并。

**理由**：华为 `eth-trunk` 和思科 `port-channel` 功能完全相同，归一成同一个词技术上很自然。但厂商串味正是这个 benchmark 要检测的现象——归一掉了，检测就失效了。

**这是全项目最有说服力的一句话。** 它证明我知道自己在测什么。

---

## D4 · 保留"进入配置模式"作为检查点 ⭐

**背景**：50 条题里 32 条（64%）把 `system-view` / `configure terminal` 列为检查点。首轮实测 qwen2.5:7b 几乎从不写这一步——**半数失败案例的唯一原因就是缺它**。

**决定**：保持不变，不降权、不改题干。

**理由**：题干写明"当前处于用户视图"，不切模式直接配置，命令贴上去设备就报错。这是硬性要求，不是格式偏好。而且"模型知道配什么、不知道要先切到哪个模式"本身就是一个有分量的发现，对应人工标注里的 `M1_视图错误`。

**代价**：会让整个 Leaderboard 的绝对数字偏低。README 里必须解释这一点，否则读者会误以为模型能力比实际更差。

**考虑过但否决的方案**：把这条降权到 0.5，或者把 context 改成"当前已处于系统视图"。两者都会掩盖一个真实的失败模式。

---

## D5 · 排障题按诊断方向判分，配置题按具体命令判分

**背景**：`hw_diag_003`（OSPF ExStart 排障）里，模型给的 `display ospf error` / `display ospf interface verbose` / `display current-configuration` 和我的参考答案完全不同，但**是一条同样有效的排查路径**，原判分只给 0.33。

**决定**：排障题的检查点改成"诊断方向"的正则族：

```
方向一 查邻居/进程状态    display ospf (peer|neighbor|error|brief)
方向二 查 OSPF 接口参数   display ospf interface
方向三 查物理接口或配置    display (interface|current-configuration|this)
```

**理由**：配置任务的可执行性是硬要求，写错就是错；排障任务的有效路径不止一条，锁死具体命令是在考记忆而不是考能力。

**放宽不等于放水**：`hw_diag_009` 改判后仍是 0.67，因为模型只覆盖了三个方向中的两个。

## D6 · 归一化的作用域限制在前两个 token

```python
toks = [aliases.get(t, t) if i < 2 else t for i, t in enumerate(toks)]
```

**决定**：缩写展开只作用于命令动词的位置，参数位置不碰。

**理由**：不能只做第 1 个（`display int g0/0/1` 里 `int` 在第二位），不能全做（参数会被改坏）。

**已知的洞**：`name q` 会被误改成 `name quit`，因为 `q` 恰好在第二位。修法要么加白名单，要么改成 `i < 1`——后者会让常见得多的 `dis int g0/0/1` 展不开。**用一个罕见的误判换一个常见的正确，是划算的。** 这条写进 README 的已知限制。

---

## D7 · 整行方括号：拆括号，不丢弃 ⭐

**背景**：首轮实测中 qwen2.5:7b 对两道 VLAN 题输出的是 `[vlan 100]` `[quit]` 这种逐行加方括号的形式。原实现把它当设备提示符整行抹掉，两条题得分都是 0.00，标签显示"无有效输出"。

**决定**：整行只有一个方括号组时，拆掉括号保留内容。

**理由**：设备提示符总是出现在命令**前面**并跟着命令。整行只有一个括号组时既可能是裸提示符，也可能是模型把命令包了起来——**漏掉一条正确命令的代价，大于多出一条无效命令的代价**（后者最多被标成命令幻觉，不影响 `passed` 判定）。

**修复后的效果**：两条题从 0.00 变成 0.83 和 0.67，并且暴露出真正的错误——**模型创建了 VLAN 但漏写了 `name` 命令**。原来那个"输出为空"的结论是假的，它把一个有价值的规律掩盖掉了。

## D8 · 命令幻觉率不参与 `passed` 判定

**背景**：词表靠人工维护，覆盖率有限。首轮实测中 `cs_ospf_007` 满分通过却被标了命令幻觉，因为 `router-id` 不在词表里。

**决定**：这个指标只作诊断信号，不进入通过判定。跑完首轮后从参考答案里扩充了词表（两个厂商各约 50 词）。

**理由**：一个靠不完整词表判定的指标，不该有否决权。README 里说明它的局限。

---

## D9 · few-shot 示例必须与题目同厂商 ⭐

**背景**：最初的 `few_shot.txt` 里写死了两个华为示例，而这个模板会被思科题也用上。等于**在提示词里主动教模型串味，然后测它串不串味**。

**决定**：模板改成 `{examples}` 占位符，`runner.build_examples(vendor)` 按题目厂商动态选取；补了两条思科示例题；加了 `test_few_shot_demos_cover_both_vendors` 守着。

**为什么值得单独讲**：这是一个**评测设计错误，不是代码 bug**——代码跑得好好的，数字也很漂亮，只是那个数字在测别的东西。**这类错误比崩溃更危险，因为它不报错。**

## D10 · 数据集自检只能保证自洽，保证不了正确 ⭐

**证据一**：草稿分隔符用错，导致 `interface GigabitEthernet0/0/0` 被切成两条命令。参考答案和检查点一起错，自检全绿。

**证据二**：批量生成脚本里检查点覆盖的编号错位一位，导致 `hw_acl_023` 没有检查"有没有创建 ACL"，却把规则检查了两遍。自检照样全绿，因为参考答案同时满足这两条。

**决定**：自检之外再加两道防线——
1. 生成脚本里加"覆盖错位检查"：每条检查点的正则必须能匹配它自己 `desc` 里那行命令
2. 首轮跑完必须人工核对（`tcb inspect`），最后对 60 条失败样本人工标注

**面试答法**：我怎么保证题目本身是对的？三层。自动自检保证每个检查点能被自己的参考答案命中，这条进了 CI；但它只能保证自洽——参考答案错了，检查点跟着错，自检照样绿。所以第二层是首轮跑完的人工核对，第三层是对失败样本的人工标注，我从中量化出评分器自身的误判率并写进了限制说明。

---

## D11 · 原始输出与评分逻辑分离

**决定**：`tcb run` 只负责调模型并把原始回答落盘，`tcb score` 全量重算分数。

**理由**：评分标准会改，模型输出不会。

**实际收益**：首轮 20 条题的核对里，我改了 7 次评分逻辑（`conf t` 归一化、方括号拆解、词表扩充、串味特征词、两条 ACL 放宽、排障题判分方式、检查点错位）。**每次都只重跑 `tcb score`，一次推理都没重跑。** 全矩阵 2160 次推理的场景下，这个设计能省掉几十小时。

副产品：原始输出全部提交在 `results/raw/`，别人可以用它复现或质疑我的判分。

## D12 · Windows 环境的两个坑

**PowerShell 5.1 的 `Get-Content` 默认按系统 ANSI（中文机器上是 GBK）读文件**，读 UTF-8 的 `models.json` 会乱码并导致 `ConvertFrom-Json` 解析失败。`run_matrix.ps1` 里必须写 `-Raw -Encoding UTF8`。

**导出人工标注 CSV 要用 `utf-8-sig` 编码**，否则 Excel 打开中文全是乱码。

这两条写进 README 的"Windows 环境注意事项"。
